Benchmarks

How fast is Ibex?

Three benchmarks, with every engine pinned to the same cores: Ibex's own in-memory DataFrame suite, the independent h2o db-benchmark and PDS-H, Polars' TPC-H-derived benchmark. Each section names the machine and the commit it was measured on. Lower is better.

Ibex's own suite

In-memory DataFrame queries

Ibex against Polars, DuckDB, ClickHouse, DataFusion and data.table on the same columnar queries, from 1M to 50M rows. Times are the mean of timed iterations.

Pick a row count and a metric. Each row is colour-scaled green→red against the best engine in that row — fastest for time, lightest for memory — and the best cell is outlined. Hover any cell for the exact time and peak memory.

What this measures. Each engine loads the data once into its own in-memory format, untimed, and every query is timed from there until its full result is materialised. DuckDB hands its result over as an Arrow table: measured against writing it into a DuckDB table, that is the faster of the two overall. Ibex's CSV reader dictionary-encodes string columns automatically, so a group-by on symbol runs on integer codes. Polars is given the same encoding (its string columns are cast to Categorical); DuckDB, DataFusion, ClickHouse and data.table group on plain strings, as they do by default. Tables are read once and queried many times, so that is a real advantage, and part of the distance to the SQL engines; Polars is the closest like-for-like comparison on this page.

Threads. Every engine gets the same box: 8 vCPU, which is 4 physical cores with 2 hardware threads each — EC2 counts hyperthreads as vCPUs, so these are 4-core numbers, not 8. Ibex parallelises some operators by default, so ibex is not a single-core number; ibex-st is the same build run with IBEX_CORES=1, which makes ibex vs ibex-st Ibex's own threading gain. polars-st, duckdb-st, datafusion-st and clickhouse-st are the equivalent single-thread runs of their engines, so ibex-st against those is the per-core comparison.

Memory. The memory metrics show absolute peak resident set size (RSS) during a query's timed iterations — the footprint to run the op, including the already-resident input table — measured per process from the kernel's high-water mark. Multi-threaded engines trade memory for the parallel speed-ups noted above.

Caveats. Every engine now materialises its full result. tf rolling EWMA uses the bounded window definition in Ibex, pandas and Polars. ClickHouse statistical/OHLC cells cannot compute correctly under the shared semantics and are excluded from claims. Each page is generated from a single run; SQLite and the data.table rolling median/std cells are omitted (they dominate wall-clock and add no competitive signal).

The code behind these numbers. Every query's exact code, in every engine, is on the Methodology & code page. Directly extracted from the harness source.

Independent benchmark

h2o db-benchmark

The h2oai db-benchmark questions, as maintained by DuckDB Labs (duckdblabs/db-benchmark, pinned at 3b074bc319): ten group-by questions on 10M rows at three key cardinalities (K=100, 10 and 2, the last with 5M groups in id3), with 5% nulls and pre-sorted variants, and five joins. None of these queries or data shapes were written alongside Ibex. Pick a data set and a core count.

What this measures. The data comes from the upstream R generators, unmodified, and every engine reads the same CSV. Polars and DuckDB use the schemas of the upstream solutions: Polars runs its streaming engine with Int32 ids and string keys cast to Categorical; DuckDB uses ENUM keys where upstream does and a FLOAT v3. Ibex declares the same string keys Categorical and otherwise picks its own types (Int64 and Float64, which move more bytes than the upstream Int32/Float32). Loading is not timed; each question runs 1 warmup and 5 timed iterations, fully materialising its result, and the table shows the fastest. Every answer is checked across engines: the row count and upstream's checksum columns must agree.

The summary rows compare Ibex with each engine over the questions all three completed: the geometric mean of the per-question ratios, and the ratio of the totals. Below 1 means Ibex is faster. The harness is benchmarking/h2o/run.py.

Independent benchmark

PDS-H (TPC-H)

Polars' TPC-H-derived benchmark (pola-rs/polars-benchmark): 22 decision-support queries over a star schema, read from Parquet. Polars (streaming engine) and DuckDB run upstream's own query code; Ibex runs its translations of the same queries. Pick a core count.

What this measures. The Parquet files come from upstream's generator, never from Ibex, and each query reads its inputs from them, as upstream PDS-H does. Every Ibex answer is diffed against Polars at the benchmarked scale before anything is timed. Times are the mean of 5 timed iterations after 1 warmup.

The summary rows compare Ibex with each engine: the geometric mean of the per-query ratios, and the ratio of the totals. Below 1 means Ibex is faster. The queries are in benchmarking/tpch/queries.
